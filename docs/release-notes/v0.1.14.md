Most of these changes come from measuring Grafana's frontend suite on warpdom, one of the applications in dom-api-tracer's candidate corpus.

- **Behavior change: each jsdom profile has only the globals that jsdom version has** (#208, #243):
  - Interfaces warpdom has before the jsdom it follows makes them globals are no longer on the window, so feature detection such as `typeof ToggleEvent !== 'undefined'` or `'CSSKeyframesRule' in window` gives jsdom's answer. Measured on jsdom's releases from 20.0.0 to 30.1.3:

    | Globals | From jsdom |
    | --- | --- |
    | `DOMRect`, `DOMRectReadOnly` | 22.0.0 |
    | `BeforeUnloadEvent` | 27.0.0 |
    | `CSSConditionRule`, `CSSContainerRule`, `CSSGroupingRule`, `CSSLayerBlockRule`, `CSSLayerStatementRule`, `CSSScopeRule`, `CSSSupportsRule` | 27.2.0 |
    | `CSSCounterStyleRule`, `CSSFontFaceRule`, `CSSKeyframeRule`, `CSSKeyframesRule`, `CSSNamespaceRule`, `CSSPageRule` | 29.0.0 |
    | `QuotaExceededError` | 30.1.0 |
    | `CSSMarginRule`, `CSSPageDescriptors`, `FormDataEvent`, `TimeRanges`, `ToggleEvent` | none yet (30.1.3) |

  - Only the global goes away, as in jsdom, whose classes exist without one: a sheet's `@keyframes` rule is still a `CSSKeyframesRule`, a details element's `toggle` event is still a `ToggleEvent`, and `video.buffered` is still a `TimeRanges`. Replacing `window.ToggleEvent` in a test no longer changes the event warpdom fires, as in jsdom.
  - The new option `beyondJsdom: true` keeps all of these globals in every profile, frames included: `createWindow({ jsdom: 26, beyondJsdom: true })`, `environmentOptions: { warpdom: { beyondJsdom: true } }` (Vitest) or `testEnvironmentOptions: { beyondJsdom: true }` (Jest). See [docs/jsdom-versions.md](https://github.com/sonukapoor/warpdom/blob/main/docs/jsdom-versions.md#globals-that-appear-in-a-later-jsdom).
- **A style rule's `style` keeps values as written, jsdom 20 to 27.0.1** (#244, #251):
  - In the jsdom 20 to 27.0.1 profiles, `sheet.cssRules[i].style` is cssom's own declaration object, as in those jsdom versions: `getPropertyValue` returns `#34363a`, `RGB(1, 2, 3)`, `var(--x)` or an invalid value as written, property names keep their case, shorthands are not expanded, there is no `item()` and no camelCase accessors, and the rule serializes as `.a {color: red;}`. warpdom used to give parsed values (`rgb(52, 54, 58)`) and drop some `var()` values in every profile.
  - `setProperty`, `removeProperty`, `cssText` (including cssom's errors) and direct writes such as `rule.style.color = 'green'` work as in cssom, and `getComputedStyle()` still sees parsed values, as jsdom's cascade does.
  - From jsdom 27.1.0 nothing changes: the rule's `style` is a `CSSStyleDeclaration` with parsed values.
- **`getComputedStyle` with a pseudo-element and no `this`, before jsdom 24** (#246): in the jsdom 20 to 23 profiles, `getComputedStyle(element, pseudoElt)` called without a `this` value (a bare call in Jest or Vitest's VM pools, where the global is the window, a destructured call, or `.call(null, ...)`) no longer reports "Not implemented: window.computedStyle(elt, pseudoElt)", as in jsdom 20 to 23. `window.getComputedStyle(...)` still reports it. From jsdom 24 both report, as in jsdom. In every version the result is the element's own style.
- **`Location`'s members are own properties** (#247): `href`, `assign`, `reload` and the other members are own, enumerable, non-configurable properties of `window.location`, as in jsdom 20 to 30, and `Location.prototype` has only `constructor` and `@@toStringTag`. So `{ ...window.location }` copies them, for example in a `jest.spyOn(window, 'location', 'get').mockReturnValue({ ...location, reload })`. As in jsdom, `Object.defineProperty(location, 'href', ...)` now throws and `delete location.assign` fails.
- **Docs: a speed-sensitive result** (#245, #248, #250): two Grafana tests that fail on warpdom because floating-ui moves the initial focus one animation frame after a drawer or modal opens, and warpdom reaches `userEvent.type` sooner. `fastFrames: true`, or waiting for the initial focus before typing, makes them pass on both DOMs. See "Results that change for other reasons" in [docs/differences.md](https://github.com/sonukapoor/warpdom/blob/main/docs/differences.md#results-that-change-for-other-reasons).
- Each DOM change was checked on 19 open-source suites plus Ant Design, Mantine, Excalidraw and wire-webapp (GitHub Actions, jsdom vs warpdom): no test changed status apart from the known, documented differences and known flaky tests.
