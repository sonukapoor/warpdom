- **`var()` with `!important` in declarations, jsdom 27 to 29** (#141, #154): in the jsdom 27.0.0 to 29.1.1 profiles, a declaration that uses `var()` (not a custom property) loses its `!important` in the style attribute, `cssText` and `setProperty()`, as in jsdom: `padding: var(--p) !important` reads `padding: var(--p);` with priority `''`. Style rules do the same from 27.1.0. In jsdom 27.4 and 28.1 a `border` with `var()` in the style attribute or `cssText` leaves the block empty, and `border-top` and the other sides with `var()` are dropped. With cssstyle 4.6.0 (jsdom 23.2, 24.1 and 26.1) a custom property in the style attribute, `cssText` or `setProperty()` loses its `!important`. Measured on every jsdom alias from 20.0.3 to 30.1.3, each with its own cssstyle.
- **Margin and padding in document order (jsdom 28.1 to 30.1.2), the later of two `!important` declarations wins (jsdom 28.1 to 30.1.3)** (#122, #155): `getComputedStyle()` applies the matching `margin` and `padding` declarations, their longhands and the style attribute in document order, as jsdom does: each one wins over the declaration that set it last only if it is `!important` over a normal one, the later of two `!important` ones, or a normal one with at least its specificity. For example `.d.d td { padding-bottom: 7px } td { padding: 8px }` computes `padding-bottom: 8px` (standard: 7px). From 28.1.0 to 30.1.3, including the latest profile, the later of two `!important` declarations wins whatever their specificity, for every property (`.d.d p { color: red !important } p { color: blue !important }` is blue). In the 28.1 and 29.1 profiles an `!important` longhand set with `setProperty()` over an `!important` shorthand loses its `!important`. Measured on 360 orders, priorities and specificities on every jsdom alias from 20.0.3 to 30.1.3.
- **The `background` shorthand: separators and `url()`** (#134, #150): a carriage return or form feed between components (`fixed\r\nno-repeat`, `red\furl(a.png)`) separates them, as in every jsdom from 20 to 30, instead of rejecting the value (before 27) or keeping it as written (from 27). Before jsdom 27 any JavaScript whitespace separates, from 27 only CSS whitespace. With cssstyle 2.3 to 4.6 (jsdom before 27), malformed `url()` components such as `url("a.png)`, `url(a.png)red` or `url(a b.png)` are rejected and the declared background stays, while `url( a.png)`, `url()` and `url("")` are accepted. Measured on jsdom 20.0.3 to 30.1.2 and cssstyle 2.3.0 to 4.6.0.
- **CSSOM edge cases** (#120, #156): in jsdom 29 and 30, a parenthesis inside a string, escape or comment doesn't end an `@supports` group, so `(font-family: "(")` matches, and `CSS.supports()` agrees in 30. Before jsdom 27.1.0 each `insertRule()` into a grouping rule gives the new rule its own `CSSStyleSheet`, a deleted rule keeps its `parentStyleSheet`, a grouping rule whose `cssRules` is set to another rule's list shares it with that rule, and the cascade follows a replaced `cssRules`. From 27.1.0 a deleted rule's `parentStyleSheet` is `null`, and so is the parent of a deleted `@import` rule's style sheet. Reparsing an `@import` rule keeps its style sheet. Measured on 14 jsdom releases from 20.0.3 to 30.1.3.
- **List iteration shaped like `Array.prototype`'s** (#127, #151): the `@@iterator` of `NodeList`, `HTMLCollection`, `NamedNodeMap`, `FileList`, `StyleSheetList`, the form collections, `RadioNodeList` and `HTMLSelectElement` (and `HTMLFormElement` from jsdom 26.1.0, `CSSRuleList` and `MediaList` from 29), and `NodeList`'s `forEach`, `keys`, `values` and `entries`, have `Array.prototype`'s names, lengths and property flags, work when borrowed for arrays and other array-likes instead of throwing `Illegal invocation`, and return iterators with the Iterator helpers. Iteration is live: `NodeList` `forEach` reads the length once and skips items removed meanwhile, and `NamedNodeMap`, a `select` and `MediaList` iterate their current items instead of a snapshot. Before jsdom 29 `MediaList` has no `@@iterator`, so spreading one throws a `TypeError`. Measured on jsdom 20.0.3 to 30.1.3. Not modeled: on the lists the functions are warpdom's own, not `Array.prototype.values` itself, which keeps `for...of` over `childNodes` at about 9 ns per item (22 before).
- **Window member setters with any receiver** (#98, #153): for the members warpdom makes on first read (interface objects, `Image`, `Option`, `Audio`, `console`, `webkitURL`, `HTMLDocument`, `WebSocket`), an assignment whose receiver is not the window (`Reflect.set(window, 'Image', 7, {})`, `super.Image = 7`, a proxy over `Object.create(window)`) gives the receiver its own property and leaves the window's member, whether or not the member was read before, as in every jsdom from 20 to 30; a proxy's `getPrototypeOf` trap is not called. An assignment through a proxy over the window replaces the window's member with a data property.
- **Focus of a disabled control with a `tabindex`, before jsdom 30.1.1** (#14, #166): in the jsdom 16 to 30.1.0 profiles, `focus()` on a disabled `button`, `input`, `select` or `textarea` that has a `tabindex` (also one inside a disabled `fieldset`) focuses it, as jsdom does until 30.1.1; Element Plus relies on this. A disabled `fieldset`, `optgroup` or `option` stays unfocusable in every profile, a documented difference: jsdom focuses one with a `tabindex` in every version. Measured on jsdom 16.4.0 to 30.1.3.
- **No `role` or ARIA properties on `Element` before jsdom 23.1.0** (#14, #166): `ariaLabel`, `role` and the other ARIA reflection properties exist only from jsdom 23.1.0, as in jsdom, so frameworks that check `key in el` (Vue) write such props as attributes on older profiles. This also corrects the jsdom 20 to 22 profiles.
- **Faster `getComputedStyle()` with many margin and padding rules, jsdom 28.1 to 30.1.2** (#158, #167): the document-order cascade for margin and padding indexes those declarations once instead of scanning every matching declaration on each call (about 101 to 11 µs per element on a page with 600 matching rules on the 28.1 profile). Results are unchanged.
- **The `warpdom compare` GitHub Action keeps one comment per working directory** (#133, #149): two working directories that share their first 199 characters, or differ only in characters the report rewrites (backticks, line breaks, `&`, `|`), got the same pull request comment marker, so one package's run could update another's report. Each now gets its own marker. Comments posted by earlier releases are still updated where their marker is unambiguous; an ambiguous one is left unchanged and a new report is posted (see [docs/compare.md](https://github.com/sonukapoor/warpdom/blob/main/docs/compare.md#github-action)).
- Each DOM change was checked on 19 open-source suites plus Ant Design, Mantine, Excalidraw and wire-webapp (GitHub Actions, jsdom vs warpdom): no test changed status apart from the known, documented differences.
