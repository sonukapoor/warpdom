- **Collections as jsdom has them** (#145, #207):
  - A `RadioNodeList` from `form.elements` is filtered again only when something reads through `form.elements` after a change (`length`, an index, `namedItem`, a named property or iteration), using the names and ids at that read, as in every jsdom from 20 to 30. It was fully live.
  - A `TouchEvent`'s `touches`, `targetTouches` and `changedTouches` are plain arrays, as in every jsdom: a copy of the list passed in, the same array on every read. warpdom's `TouchList` is removed, so `Array.isArray(e.touches)`, `.map()`, snapshots and `toStrictEqual` see what they see in jsdom.
  - There is no `CSSRuleList` global before jsdom 29. From jsdom 27.1 to 28, `CSSKeyframesRule` has jsdom's own `name` and `cssRules` properties, index getters and iterator.
- **Shadow trees: iframes and moving a host to another document** (#205, #211, #204, #226):
  - From jsdom 30.1.0, an iframe in a connected shadow tree gets a window, as in jsdom; before 30.1.0 it gets none. warpdom used to give it one or not depending on insertion order.
  - In every version, shadow-tree iframes are not counted in `window.length`, `frames.length` or `window[0]`, `window[1]` and so on. Removing one discards its window and aborts its pending requests.
  - jsdom 30.1 keeps `contentWindow` after a shadow-tree iframe is removed; warpdom returns `null`, as for every removed iframe.
  - A shadow host moved to another document takes its shadow trees along, nested ones included: their `ownerDocument`, computed style, slots, ranges, observers and custom elements follow the new document as in jsdom.
- **`warpdom compare` without `--baseline`: files put on a DOM by a comment or `environmentMatchGlobs`** (#181, #212):
  - A project whose config chooses no DOM (for example `environment: 'node'`), but whose files choose jsdom or happy-dom with a `@vitest-environment` or `@jest-environment` comment or with Vitest's `environmentMatchGlobs`, is now compared. compare used to stop with "nothing to compare" (exit 2), or leave those files out.
  - Only those files are compared; the rest of a `node` project stays out. The report lists the files `environmentMatchGlobs` put on jsdom.
  - A project with no DOM at all now costs one test run before "nothing to compare".
- **`warpdom migrate`: commented files, configs it can't read, workspaces** (#200, #217, #221, #231, #233, #235):
  - A `@vitest-environment` comment counts for the Vitest projects that run the file (inline `test.projects` and `test.workspace`, `defineProject`, with their `root`, `dir`, `include` and `exclude`), not for the whole package. A project the pin doesn't reach gets a note listing its files, and the profile reports `same: false`. Files that can't be mapped get one note and `same: null`. `@jest-environment` comments still count per package and runner.
  - A file whose comment says jsdom, in a project that names `environmentOptions.warpdom.jsdom`, ran on the installed jsdom and will follow the named version on warpdom: migrate reports it per file.
  - Config forms migrate can't read count as unknown (`same: null`) instead of unchanged: environment options that aren't object literals, a jsdom version given as a variable, computed keys other than `['x']`, and `defineConfig` callbacks whose returned object isn't clear.
  - In a workspace whose root declares jsdom, `--apply` writes the jsdom pin into the sub-package config it edits, instead of asking you to add it by hand.
- **`:empty` and text changes** (#202, #218):
  - Any text child, even an empty one, makes an element non-empty for `:empty`, as in every jsdom from 20 to 30. Comments and processing instructions still don't count.
  - Text changes (`data`, `appendData`, `textContent`) refresh computed style and query results that depend on text, for example `textarea:invalid` and `:dir()` on a `dir=auto` element. In the jsdom 21 to 30.1.1 profiles, a text change in a disconnected tree or a shadow tree still keeps kept computed values, as in jsdom.
- **Computed colors per jsdom version** (#193, #219, #199, #223):
  - `color-scheme: dark`, jsdom 27 to 29.0.1: only a root (the `html` element, the top of a detached tree or of a shadow tree) turns white. A connected element keeps the color it inherits.
  - `color-scheme: dark`, from jsdom 29.0.2: an element with its own `color-scheme`, whose color nobody up the chain declares, turns white, and its `currentcolor` (its border colors, for example) is its parent's color. A declared color, such as `body { color: red }`, wins in every version.
  - In the jsdom 27 to 29.0.1 profiles, `inherit`, `initial` and `unset` resolve to values for `color`, `background-color`, the border colors, `caret-color`, `display`, `pointer-events` and `visibility`, and `outline-color: inherit` gives the parent's value. They used to stay as written.
  - In the jsdom 22.1 to 29.0.1 profiles, only `color`, `background-color`, the border colors, `outline-color` and `caret-color` resolve colors. `fill`, `stroke`, `text-shadow`, `accent-color` and the other color properties compute as declared.
  - From jsdom 29.0.2, a color property computes from its first component: `scrollbar-color: red blue` gives `rgb(255, 0, 0)`, and `auto` or `none` give `rgba(0, 0, 0, 0)`. `color-mix()` in srgb is computed, and `inherit` on `box-shadow`, `text-decoration`, `outline`, `column-rule` and `caret` gives the parent's value.
- **`url()` and `var()` in style values, per jsdom version** (#144, #220, #222, #232, #234, #238):
  - `url()` is read as CSS Syntax 3 reads it, with each version's escaping: jsdom 27 and 28 escape only `"`, and from 29, `\` and control characters too. jsdom 27 rewrites a valid `url()` only in `background` and `background-image`; from 28, a value that is a single `url()` is rewritten in any property except `cursor`.
  - From jsdom 27, a line break inside a quoted `url()` string is a bad string in `cssText`, the `style` attribute and style sheets. In jsdom 20 to 26, a `style` attribute or `cssText` with an unclosed string or parenthesis declares nothing.
  - jsdom 23 to 30 treat `var(` as `var()` only when it is lowercase and starts the value or follows whitespace, `(`, `/` or `*`. So `VAR(--a)`, `red,var(--a)` and `url("notvar(x).png")` are no longer taken for `var()`, and `var()` values with unbalanced or unclosed parentheses are kept where jsdom keeps them. jsdom 20 to 22 and 25 still drop any value with `var(` in it.
  - An escaped parenthesis in a `url()` beside `var()` (`var(--a) url(a\(b c.png)`) is kept from jsdom 27, and through `setProperty` in 23, 24 and 26.
  - Setting values with `var()` through `cssText` is about 20% faster, because they are no longer tokenized.
- **Window members locked before their first read** (#160, #227): `Image`, `Option`, `Audio`, `console`, `webkitURL`, `HTMLDocument`, `WebSocket` and the interface objects can be read and assigned after `Object.defineProperty(window, name, { configurable: false })`, `Object.seal(window)` or `Object.freeze(window)`, as in jsdom, instead of throwing `Cannot redefine property`. (jsdom before 27 throws on `Object.seal` and `Object.freeze` of the window; warpdom allows them in every profile.) On a frozen window, strict assignments throw jsdom's read-only error. The property is still an accessor, where jsdom has a data property.
- **Fast mode: a setup file's mocks of globals** (#201, #228, #230, #236):
  - The per-file reset follows each `vi.stubGlobal` and `vi.spyOn` on `globalThis` from its first mock to the cleanup that undoes the last one (`vi.unstubAllGlobals`, `vi.restoreAllMocks`, `mockRestore`, and the `unstubGlobals` and `restoreMocks` options), instead of comparing property descriptors.
  - A global set by a module loaded once per worker, then mocked by a setup file, gets that module's value back after cleanup, not the mock. Before, every later file's mock recorded the earlier mock as its original.
  - Spies on both accessors of a member (`pageYOffset`, for example) are both undone before the next file. Mocked members are restored even after a file whose tests were all skipped.
  - Checked on Vitest 4.1 and 5.0. A test that replaces a global without `vi` (#192), and `vi.spyOn(window, ...)` in the VM pools, are not followed.
